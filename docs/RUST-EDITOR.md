# 用 Rust 製作店面編輯器：可行性評估

第 192 項，店主 2026-11-16：「幫我評估用Rust來製作編輯器的可行性」。第 187 項當時只在對話裡簡短回答，這份是正式的評估：先量編輯器的時間花在哪，再盤點要搬的東西，比較四條路，最後給建議。

## 結論

1. **技術上可行，但不建議整個編輯器改用 Rust 重寫。**
   - 要把店面的 3D 再做一份：4.3 萬行的擺設程式、457 處程式產生的幾何、38 處自訂著色。之後遊戲與編輯器兩份畫面要一直對齊。
   - 重寫要幾個月，換來的只有編輯器變快，遊戲不會。
2. **編輯器現在卡的不是 JavaScript，是 WebGL 送繪製。**
   - 一格裡 83～86% 的 CPU 時間花在 three.js 把約 1,400～1,500 次繪製送給 WebGL，每次約 8～9 微秒。
   - 我們自己的程式只佔 1.6～6.3 ms。
   - 遊戲本身也一樣重：編輯器沒有比遊戲多畫。
3. **想要「真的桌面工具」**：用 Tauri（Rust 寫的桌面外殼）包住現在的編輯器，約 2～4 天。
   - 得到獨立視窗。
   - 存檔可以直接寫進專案的檔案，不再要把 offset 數字抄給雲端 chat 寫成預設值。
   - 畫面還是同一份，沒有兩份要對齊。
   - 要下載 Tauri 的套件，照守則要店主同意。
4. **想要更順**：減少繪製次數，遊戲與編輯器一起變快。這比用 Rust 重寫划算得多。

## 1. 量測：時間花在哪

量法：`tests/e2e/_rust192.mjs`（在 git 外），在這台電腦的真顯示卡上跑（headless Chrome＋ANGLE Direct3D 11），不鎖每秒畫面數，每個情境 5 秒。

- 主執行緒、JavaScript、樣式與排版：從 Chrome 的 Performance 指標換算。
- three.js 的繪製：把 `renderer.render` 包起來計時。
- 每格更新：把每一個 `useFrame` 包起來計時。
- 顯示卡：用 WebGL 的計時查詢（`EXT_disjoint_timer_query_webgl2`）量 render 在 GPU 上花多久。

因為加了計時，數字比平常略低。第 186 項沒加計時時，拖曳量到 66 fps。

| 情境 | 每秒畫面 | 一格 | 主執行緒忙 | three.js 送繪製 | 每格更新 | React 與編輯器 | 顯示卡 | 繪製次數 | 三角面 |
|---|---|---|---|---|---|---|---|---|---|
| 編輯器・閒置 | 72.6 | 13.8 ms | 13.9 ms | **11.4 ms** | 1.1 ms | 0.9 ms | 8.1 ms | 1,404 | 42.7 萬 |
| 編輯器・轉鏡頭 | 64.8 | 15.4 ms | 15.5 ms | **12.2 ms** | 0.8 ms | 1.4 ms | 9.3 ms | 1,453 | 44.8 萬 |
| 編輯器・拖一件擺設 | 47.4 | 21.1 ms | 21.3 ms | **12.8 ms** | 0.7 ms | 5.5 ms | 14.0 ms | 1,522 | 47.1 萬 |
| 遊戲・閒置（對照） | 65.6 | 15.3 ms | 15.6 ms | **13.1 ms** | 0.7 ms | 1.3 ms | 9.7 ms | 1,508 | 57.0 萬 |
| 遊戲・轉鏡頭（對照） | 60.4 | 16.6 ms | 16.7 ms | **13.9 ms** | 0.6 ms | 1.4 ms | 10.9 ms | 1,522 | 57.2 萬 |

怎麼讀：

- **主執行緒一直是滿的**（一格 13.8 ms，忙 13.9 ms），所以先卡住的是 CPU，不是顯示卡。
- CPU 的時間大部分在 **three.js 送繪製**：一格約 1,400～1,500 次繪製，每次約 8～9 微秒。WebGL 的每一次呼叫，都要經過瀏覽器的檢查、送到 GPU 行程、由 ANGLE 翻成 Direct3D 11。這是 WebGL 本身的成本，three.js 或我們的程式都省不掉，只能少送幾次。
- **我們自己的程式很少**：每格更新 0.6～1.1 ms，React 與編輯器 0.9～5.5 ms。拖曳時那 5.5 ms 是被移動的那件擺設與面板跟著更新；第 186 項已經把「每一件擺設都跟著重畫」拿掉（拖曳 27 → 66 fps）。
- **顯示卡**一格 8～14 ms：畫同樣的三角面、同樣的像素，用什麼語言都一樣。

## 2. Rust 能省到哪一塊

- **能省**：送繪製的 CPU 時間。原生程式（Rust 的 wgpu → Direct3D 12／Vulkan）每次繪製的 CPU 成本一般在 1～2 微秒，同樣 1,500 次約 2～3 ms。這是一般的數量級，沒在這台電腦上量過；要量得先下載 wgpu 做一個小測試。
- **省不到**：顯示卡的 8～14 ms。所以就算 CPU 省下來，上限大約是 70～120 fps；拖曳的情境（顯示卡 14 ms）大約 70 fps。
- **只有編輯器變快**：玩家看到的遊戲還是 WebGL，一樣是 13 ms。
- **同樣的節省，在現在的程式裡也拿得到**：
  - 減少繪製次數：把不會動的零件合併得更多，重複的東西用 instancing。目前 1,500 次裡有多少能省，要用 `perf.mjs BY=1` 一件一件看。
  - 之後換 three.js 的 WebGPU renderer：每次繪製也便宜很多，但 38 處自訂著色要改寫。
  - 兩條都是遊戲與編輯器一起受益。

## 3. 用 Rust 重寫要搬什麼

| 項目 | 規模（2026-11-16） | 在 Rust 裡要怎麼辦 |
|---|---|---|
| 店面的 3D：擺設、灶台、吧台、客人、員工、廁所、飲料櫃… | `src/shops/grill` 59 檔、43,535 行；194 件擺設；程式產生的幾何 457 處；每格更新 125 個 | 全部重寫；或從遊戲匯出一份靜態快照（glTF）給 Rust 讀，但快照裡沒有會動的人、動線、炭火、營業流程 |
| 外觀：卡通光影、描線、滑鼠指到的發亮、兩條燈光線路、圓窗外的景色 | three.js 的材質，自訂著色 38 處（22 檔） | 用 WGSL 重寫，再對一次店主定案的外觀（固定規則 8～10） |
| 模型 | 78 個 glb、21 MB，76 支 Blender 腳本 | 可以直接讀：glTF 是標準格式，Rust 有現成的讀取 |
| 編輯器本身：選取、移動旋轉縮放把手、群組、軸心、復原、階層、屬性、動線圖、禁區、渲染設定、角色預覽、選單 | `edit.ts`、`Movable.tsx`、`EditorShell.tsx`、`PathMap.tsx`、`PathZone.tsx`、`renderPrefs.ts`，共 3,449 行 | 重寫，例如用 egui 加 transform-gizmo 之類的套件 |
| 存檔 | 瀏覽器的 localStorage，遊戲讀同一份 | 改成檔案，遊戲也要改成讀檔 |
| 之後每加一件擺設 | 一份程式 | 兩份（遊戲一份、Rust 一份），要一直對齊 |

## 4. 四條路

| 做法 | 工作量 | 得到什麼 | 風險與代價 |
|---|---|---|---|
| **A. 整個用 Rust 重寫**（Bevy，或 wgpu＋egui） | 讀遊戲快照的簡化版約 3～6 週；跟遊戲一模一樣約 3～6 個月 | 編輯器的 CPU 變快，原生程式 | 兩份 3D 要一直對齊；外觀會不一樣；快照版看不到會動的東西；遊戲不受益 |
| **B. Tauri 桌面殼**（Rust 外殼＋現在的編輯器網頁） | 2～4 天 | 獨立視窗的桌面工具；存檔直接寫進專案的檔案；可以多視窗（角色預覽獨立一個視窗）；看到模型檔變了自動重載 | 畫面速度跟現在一樣（Windows 的 WebView2 也是 Chromium）；第一次要下載 Tauri 的套件（Rust 的 crates 與 npm 的 `@tauri-apps/cli`），編譯快取約數百 MB |
| **C. 只把重的計算改成 Rust**（編成 WebAssembly） | 每塊 1～3 天 | 那一塊的計算變快 | 現在量不到值得搬的計算：每格更新只有 0.6～1.1 ms；以後動線尋路、穿模檢查變重時再看 |
| **D. 維持網頁，繼續優化** | 減少繪製次數約 2～5 天；換 WebGPU 約 2～4 週 | 遊戲與編輯器一起變快 | 換 WebGPU 要把 38 處自訂著色改寫，再對一次外觀 |

## 5. 建議

1. **不整個用 Rust 重寫（A）**：花幾個月，換來的是只有編輯器變快，3D 要維護兩份。卡的那一塊（WebGL 送繪製），在現在的程式裡也減得下來。
2. **想要「真的桌面工具」就做 B（Tauri）**：Rust 只當外殼，畫面還是同一份。最大的好處是存檔直接寫進專案。
   - 第一步：Tauri 專案放在 `tools/editor-app/`，開發時連 `npm run dev`，發佈時打包 `dist/editor.html`。
   - 第二步：「儲存」改成寫專案裡的版面檔，遊戲把它當預設值讀。
   - 飲料庫存的 `jgs-drinks-1` 不動：它在遊戲的瀏覽器裡，桌面殼碰不到。
3. **想要更順就做 D 的第一步**：用 `perf.mjs BY=1` 找出繪製次數最多的擺設，把約 1,500 次往 800 以下降（遊戲與編輯器一起受益）。可以排進待辦。
4. **C 先不做**：等量到某個計算真的慢再做。

## 6. 需要店主決定的

- **要不要做 B（Tauri）**：要的話說一聲。要下載 Tauri 的套件，照守則下載要店主同意；同意後我在 `tools/editor-app/` 建專案，先做「存檔寫進專案」。
- 不做的話不需要做任何事，編輯器照現在的網頁版繼續用。
